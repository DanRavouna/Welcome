# Notes from six Critter Roll sessions (Nov 3 to Nov 7, 2026)

Source: the transcripts of six Claude Code cloud sessions, read in full, plus the two documents the last session produced (`docs/next-plan.md` and `engine/format.md` on the editor branch). Dan's words are quoted exactly as typed, typos included. Nothing here is from memory of the game itself.

## Per session

### 1. "Critter Roll setup and deployment" (Nov 3)
**Creation.** Input: a source archive from an earlier chat, a handoff file, six rules and two public Supabase values, in one opening message. Order: unpack, rebuild, publish to GitHub Pages, write the rules file, run the 30 existing suites (push held until all passed), then, on Dan's word, cloud saves with a real end-to-end test. The game already existed; this session gave it a home and a memory between sessions.
**Iteration.** Triggered by Dan not seeing the gap between "published" and "my saves follow me": "Something I dont understand, what i want is to play and that my saves follow automatically". An intermittent failure chased for 20 minutes was the test's own artefact.
**Meaning.** None discussed.
**Dan's words.** Opening brief: "This first task only publishes the current game. Do not start online features yet." Then: "Allow"; "How do i continue developping ?"; "The website is working no 404"; "I want you to do everything"; "I want to resume development soon, once the saves are working can we go back to working on the game? should i make a new context?"; "i d like to test the saves feature"; "I want to resume work, how do i create a channel w the git info and right memory i guess?"
**Lesson.** The project's memory was placed in two repo files (rules + handoff); every later session leans on them. Dan's concern was continuity ("right memory"), not features.

### 2. "Token usage and speed" (Nov 4)
Dan asked "Is there a way of using more tokens for you to be faster ?"; the answer was mostly no (parallel tool calls and parallel test groups are the only trade). Two lines, as requested; nothing else happened in this session.

### 3. "Game hosting on GitHub" (Nov 5)
**Creation.** Nothing built. Two assessments: hosting is within GitHub's terms (except that a password form on a Pages site goes against GitHub's guidance), and multiplayer ranges from small (marks left for others) to large (live fights), with the structural problem that each phone owns its save.
**Meaning.** The one session where Dan wrote a meaning sentence himself, for a feature that does not exist: "Id say the meaning is that even if we carry our own light, we all look for it at the same time". The AI said player-versus-player killing pulls against it (the revamp had removed conquest wording) and offered "We each carry our own light, but we are all out in the same night". Dan kept the ambush idea anyway.
**Dan's words.** "isnt this against github toc?"; "ok we re fine then, also i used to talk about making this game online, meaning multiple people could play at the same time, can you assess the difficulty of such a task"; "1 this game is just for fun for now, we ll setup anti cheat mesures lates / 2 cant we host the game in a general server and everyone logs in it? / 3 cant the time be based on the server? / 4 Id say the meaning is that even if we carry our own light, we all look for it at the same time / For the options / No trading critters, they can fight eachother and kill eachother, same the server handles it i guess? / Review my answer and advise, no work yet this is purely informationnal"; "I d like it that players dont need to accept duels they can just be ambused".
**Lesson.** Dan decides by taste first (ambushes, no consent) and treats the meaning conflict as an open question, not a veto. Two decisions were left open (what losing costs, where ambushes are allowed).

### 4. "Critter roll notes to-do" (Nov 5)
**Creation.** A to-do section in the handoff, nothing else. Each note was written down with the AI's own "needs a meaning sentence first" attached.
**Dan's words (the notes).** "Critter roll notes, please keep in memory in a to do list / should be online eventually"; "visuals of the houses should be updated"; "attacks should be unlocked as we evolve, start w 1 attack, then 2, then 3, then 4 for the ultimates"; "For now it s only notes, we keep them that way when we re out of tasks we can look into them"; "set up events w storyline"; "update general visuals of the world, lots of places are lines missing rocks and little formations to make it lively"; "Review my notes and ask me questions"; "2 mossbrook / 1 let them as is for now this is a later task anyway"; "We start on nothin in this convo it s for tracking only"; "We need to vary the attacks, currently they all do the same attack just at different intensities, also the vfx needs more work".

### 5. "Batch tests performance issue" (Nov 5)
**Creation.** Nothing changed in the repo; the suite was measured (30 default tests, 363 s, half of it fixed sleeps). Parallel groups and a smoke group were proposed; both exist in later sessions.
**Dan's words.** "I ve notices that running the batch of tests takes around 10mins plus, what is the reason ?"; "Dont change anything, the tests take like 10 mins so we re still missing some issues options ?"; "Give me ways of running parallel tests,".
**Lesson.** Dan treated a slow test suite as a sign of *coverage gaps*, not just a cost ("so we re still missing some issues"). The fix adopted was structural (groups, parallelism), not shaving waits, since the rules require animated things to be tested over real time.

### 6. "Game migration to RPG Maker" (Nov 7) — the long one

**What was attempted, in order (all times UTC).**
1. 02:01. Dan: "How difficult is it to move the game to rpg maker but keep the github play online part active ?" Assessment: keeping the web hosting is easy (RPG Maker exports a web folder); moving the game is close to a full rewrite (9,000 lines of custom engine, real-time combat, procedural music, cloud saves, 78 tests, and the meaning rules would all push against RPG Maker's defaults). The AI asked what Dan actually wanted from RPG Maker.
2. 02:03. Dan: "I d like an editor to create the maps myself so using rpgmaker would help w that". The AI read the map code: a map is a character grid, one letter per tile, many maps generated from seeds plus hand-placed cities, props and exits placed by search logic after the grid exists. Recommendation: "You'd get a nicer editor and lose the game you've built"; build an editor into the engine instead.
3. 02:08. Dan: "Ok food for thought, can you make me an editor i can use the same way i launch the game". First editor built in an hour: a page beside the game that paints the game's own letter grids using the game's own renderer, saving only *changed cells per map* (a patch over the generated maps), with a walkability check (every exit and door reachable from spawn), Playtest, Export. Only plain terrain paintable; buildings, signs, objects stayed code-placed. Dan interrupted mid-test: "Explain to me what i want". The AI restated the goal (draw maps by hand, keep the game online as is) and its assumptions. The handoff got a meaning line written by the AI: "the roads are kept by someone; now Dan keeps them by hand."
4. 02:21. Dan: "I would host the engine in claude since we dont need to share it". The editor became a private claude.ai page; the draft had to travel to the live game through the URL because the page cannot share browser storage with GitHub Pages.

Built: Submit runs the walkability gate, asks one line "what do these edits mean inside the quest" and uses it as the commit message, writes the edits file through a GitHub connector, and a workflow rebuilds, runs smoke tests and deploys. Dan: "Force-push it and push the workflow to main". The workflow was proven on GitHub's runner (27 tests in 71 s).
7. 03:27. Dan: "Water looks weird when set by hand in the editor". Checked in the real game: water was fine; the "tiles" were the editor's gold marker on every edited cell. Changed to one outline per edited region.

10. Dan: "Ask me one question at a time". 11. 14:18. The plan (`docs/next-plan.md`): engine boundary measured, layout (`engine/ editor/ next/ legacy/ site/`), formats v1, editor screens, six milestones each tested and pushed, risks said plainly, three open questions. Dan: "Go".

Meaning sentence deferred; tools built anyway on the stated ground that "the engine and the editor can be built first because they are tools, not statements."

## Overall

### Creation
In order: a home for an existing game (hosting, rules, handoff); cloud saves; a to-do list; a test runner shaped by a performance question; a map-painting editor; then a pivot to a reusable engine with a versioned content format, a whole-map editor, and a new empty game. The inputs were almost always a one-line wish from Dan followed by the AI measuring the code before proposing. The biggest piece of creation (the engine cut) came from a *reading* of the code's structure, not from a feature request.

### Iteration
Triggers: Dan trying the thing on a phone and finding it unusable (three interface reworks in 25 minutes); things that looked wrong but were not (the water); things that silently did nothing (blocked dialogs, a missing connector); the suite catching real breakage. Thrown away: the RPG Maker route (never started); the patch-over-generated-maps editor (replaced by whole-map data); the Submit-from-page path (never worked in Dan's account); the first game itself (frozen as `legacy/`), for a structural reason in Dan's words: "the structure is too confusing and the scope too large".

### Meaning
Meaning entered as a rule already in the repo (meaning first; hint and play, don't tell) and was carried by the AI as a reflex: every note got "needs its meaning sentence", Submit asked for one line of meaning as the commit message, the placeholder maps were made deliberately meaningless, no people were shipped without a sentence. Dan wrote a meaning sentence exactly once, for multiplayer, and let it stand in tension with his taste. Asked for the new game's meaning he answered "Not decided yet", and the work went ahead on tools. Where it failed: the AI-written meaning for the first editor ("now Dan keeps them by hand") is a rhyme, not a mechanic, by the project's own rule; and the handoff records that the theme was read out of existing text by the AI and confirmed by Dan rather than written by him. Implied: meaning here is a gate the AI holds and Dan passes through when he has something to say, not a thing Dan starts from.

### Dead ends and the lesson
- RPG Maker: an editor bought at the price of the game. Lesson: ask what the person wants *from* the tool before weighing the tool.
- Patching generated maps: the editor "only works because it paints the grids that file generates." Lesson: an authoring tool over code-generated content exposes the code as the real problem.
- Submit from a hosted page: three layers of sandbox and account plumbing, the last (no connector) unfixable from the session. Lesson: verify the account side before building a one-button publish.
- "never merge to main" caused rebase conflicts within the hour and a blocked force-push. Lesson: separation by branch is costly when both sides move.
- The "safe" recommendation was overruled twice (keep the old game playable; text commands for events): Dan preferred the cleaner break and the form that needs no typing on a phone.

### What a designer hands to the engine, and in what form (from the RPG Maker session)
- **Maps**: one JSON file per map. Size, a `grid` of `H` strings of `W` single letters (ground, path, water, tree, rock, fence, cave wall, tall and rare grass; room letters for wall, floor, rug, door mat, bed, shelf, table, stove, chest), a palette name and theme preset, `places` (buildings: footprint, roof, door tile, which room they enter), `props` (landmark kinds by name, footprint from the engine), `exits` (an edge, a tile span, a target map) with `arrive` and `arriveFrom` spots, a `spawn`. Rooms are maps with `interior: true` and a style. An index names the start map. The editor writes all footprint and gap letters itself; "you never edit these by hand".
- **People**: `{ id, name, x, y, look, facing, still, lines }`; looks are named palettes in one file over one sprite body. The plan adds a `when` condition on flags so one person can have several states.
- **Events (planned, not yet built)**: a script is a list of step cards with fixed fields, no syntax: Say, Choice, Set flag, If, Jump, Teleport, Move person, Face, Wait, Open/close, Show/hide, Set tile, Music, Time, Sound, End. Conditions are one comparison of a flag, combinable with all-of/any-of; no loops, no arithmetic beyond add 1. Flags live in the save. Triggers are tiles with a script and a `once` flag. One small interpreter with one test per step, Wait and Move tested over real time. Stated limit: "easy to author and hard to make expressive".
- **The test of data-ness**: every map must survive `JSON.parse(JSON.stringify(map))` with nothing lost and hold no functions.
- **What stays code**: hooks the game passes into the engine (combat, object art and light, under/over drawing, callbacks); a new region is a palette entry plus a preset; a new look is drawing work. The new game's own code was 30 lines at milestone 2.
- **Delivery**: one exported bundle, split into per-map files, inlined by the build. The editor draws with the engine's renderer so authoring and play match pixel for pixel. Submit was meant to carry one line of meaning per commit; that never reached the repository.

### What could not be judged from the cloud
Feel under a thumb, long-press delay, tile size, walking with a joystick, anything on a real phone or network. Every report ended with a "not verified" list; Dan's "Unusable" and "too hard to use" were the only tests of feel that happened.
